## Acuerdo de interfaz propuesto
Se adopta el contrato candidato de campaign-state-qa01.md (commit aa98c48) en vez de añadir otra ficha o motor. El servidor construye access desde identidad autorizada; el navegador no determina rol, campaña ni autoridad de estado. El adaptador server-only simulation/narrative-projection.mjs obtiene el evento a través de playerState y exige recibo confirmado y revisión válida. No recibe el árbol, estado especulativo o datos privados como entrada editorial. Aún no existe endpoint autenticado: esta frontera es una función interna, no seguridad de transporte.
Salida: {schemaVersion:1,kind:"confirmed-narration",campaignId,actorId,revision,eventId,locale:"es-AR",narratorVersion:"narrative-confirmed-v1",presentationStatus:"fallback",presentation:{id,revision,phase,title,roman,text,checks}}. Cada check conserva ID y valores de la proyección del motor. text contiene cadenas o tokens {check:id}, con cada chequeo exactamente una vez. No HTML de modelo. Sólo acciones soportadas actualmente: consume-ration, travel, duel. Fallback determinista a partir de tipos de hechos confirmados, sin inventar heridas, diálogos ni resultados. No se presenta un número de tirada fuera de su componente. Los nombres de destino proceden de nodos visibles; revisar conocimiento histórico por evento antes de habilitar re-narración con contexto cambiante.
El componente book-narrative-event existente añade setConfirmedNarration(envelope,scope), que valida estructura y ámbito y reutiliza book-skill-check. No se añade lector ni ruta nueva. Volver a renderizar reemplaza nodos, no duplica tiradas. La validación cliente detecta errores de estructura, no sustituye ACL. El lector aún muestra el prototipo anterior al abrir normalmente; el adaptador sólo se ejercita en prueba de integración. No se publica proyección de campaña en archivos estáticos.

## QA-08 / seguridad
La proyección narrativa se construye sólo desde journal visible y recibo; no serializar state, seed, receipts, previewHash ni packet Ripple al cliente. Una lista permitida de campos no garantiza que texto libre de upstream esté libre de secretos: la simulación debe revisar semántica de reason/formula y nombres; el LLM debe recibir sólo contexto autorizado y validación de hechos antes de entregar prosa. No se afirma protección frente a acceso HTTP, caché o manipulación persistente: QA-03 pendiente.
Las fichas de autoría de Stormkeep publicadas son documentos administrativos, no proyección de jugador. Las agendas privadas se mantienen fuera de Hosting. No incluirlas en jobs o logs públicos.
